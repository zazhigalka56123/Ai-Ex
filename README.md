# «Привет, спишь?» — лабораторная работа 3

Система разделена на три бизнес-сервиса. Каждый запускается отдельным процессом, получает настройки из Spring Cloud Config Server и регистрируется в Eureka. Внешние HTTP- и WebSocket-запросы проходят через Spring Cloud Gateway.

| Модуль | Назначение | Хранилище | Порт |
| --- | --- | --- | --- |
| `app` / `core-service` | Персоны, импорт переписок, диалоги, LLM-агент, консультации, модерация | PostgreSQL + JPA | 8083 |
| `iam-service` | Пользователи, роли, проверка текущего пользователя | PostgreSQL + JPA + Reactor | 8081 |
| `notification-service` | Доставка и история уведомлений | PostgreSQL + R2DBC + WebFlux | 8082 |
| `config-server` | Централизованные настройки из `config-repository` | Native configuration repository | 8888 |
| `discovery-server` | Eureka Service Registry | — | 8761 |
| `gateway` | Маршрутизация и Circuit Breaker | — | 8080 |

`shared-kernel` содержит общие типы и контракты, `shared-web` — инфраструктуру MVC, `shared-security` — общую проверку и выпуск JWT. Эти модули не являются запускаемыми сервисами и не содержат бизнес-репозиториев.

## Запуск

Нужны Docker с Compose; для локальной сборки — JDK 21. Gradle Wrapper включён в репозиторий.

Перед первым запуском скопируйте `.env.example` в `.env` и задайте:

- `JWT_SECRET` — случайный секрет не короче 32 байт, общий для Gateway и трёх бизнес-сервисов. Например, его можно получить командой `openssl rand -hex 32`.
- `BOOTSTRAP_ADMIN_EMAIL` и `BOOTSTRAP_ADMIN_PASSWORD` — данные первого супервайзера. Пароль: от 12 символов, не больше 72 байт UTF-8.

Секреты не заданы в репозитории. Первый супервайзер создаётся при старте IAM; если выбран существующий демо-администратор без пароля, ему назначается пароль. Повторный запуск не сбрасывает установленный пароль и не повышает роль существующего обычного пользователя.

```sh
docker compose up -d --build --wait --wait-timeout 600
```

Если Compose установлен отдельной командой, используйте `docker-compose`.

- Веб-интерфейс: http://localhost:8080/
- API и Swagger UI: http://localhost:8080/swagger-ui.html
- В общем Swagger UI выберите `core`, `iam` или `notifications`. Спецификации и запросы «Try it out» доступны через Gateway; внутренние `/internal/**` не публикуются в документации.
- Eureka: http://localhost:8761
- Конфигурация: http://localhost:8888/core-service/default

Compose запускает три независимых PostgreSQL с отдельными пользователями, базами и томами. Данные лабораторной №1 не изменяются: используется новый Compose-проект `ai-ex-lab2`. Доступ к бизнес-сервисам с хоста идёт через Gateway; внутренние `/internal/**` маршруты наружу не публикуются.

```sh
docker compose down
```

Для запуска без контейнеризации JVM:

```sh
docker compose up -d core-db iam-db notification-db
./gradlew bootJar
java -jar config-server/build/libs/service.jar
java -jar discovery-server/build/libs/service.jar
java -jar iam-service/build/libs/service.jar
java -jar notification-service/build/libs/service.jar
java -jar app/build/libs/service.jar
java -jar gateway/build/libs/service.jar
```

При локальном запуске экспортируйте `JWT_SECRET` для всех бизнес-сервисов и Gateway, а `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` — для IAM.

Команды `java` запускаются в отдельных терминалах из корня репозитория, сначала Config Server и Eureka. Адрес Config Server задаётся `CONFIG_SERVER_URL`, Eureka — `EUREKA_URL`. Настройки подключения к БД задаются `CORE_DATABASE_*`, `IAM_DATABASE_*`, `NOTIFICATION_DATABASE_*`; значения по умолчанию находятся в `config-repository`.

Конфигурации сервисов хранятся в `config-repository/<spring.application.name>/application.yaml`. Общие настройки Eureka, Feign и Resilience4j находятся в `config-repository/application.yaml`; настройки конкретного сервиса имеют приоритет. Config Server ищет файлы в корне репозитория и в каталоге `{application}`, поэтому конфигурации разных сервисов не смешиваются. `CONFIG_REPOSITORY` задаёт корень репозитория (например, `file:/config-repository`). Локальные конфиги запуска также называются `application.yaml`, тестовый — `application-test.yaml`.

## Взаимодействие

Gateway направляет `/api/v1/users/**` и `/api/v1/auth/**` в IAM, `/api/v1/notifications/**` — в сервис уведомлений, остальные API и `/api/v1/conversations/*/ws` — в core. Адреса сервисов определяются через Eureka и Spring Cloud LoadBalancer.

Core проверяет пользователей, получает имена специалистов и метрики через OpenFeign. Сервис уведомлений также проверяет пользователя через Feign; блокирующий вызов выполняется на `boundedElastic`, вне Netty event loop.

IAM возвращает `Mono` из контроллеров. Вызовы транзакционных JPA-сервисов выполняются лениво через `Mono.fromCallable(...).subscribeOn(Schedulers.boundedElastic())`; DTO формируются на том же рабочем потоке. JPA остаётся блокирующим, его транзакции не переносятся между потоками.

Уведомления сохраняются и читаются через Spring Data R2DBC и Reactor. Контроллер возвращает `Mono` с телом ответа, заголовки пагинации устанавливает через `ServerHttpResponse`. Реактивный `WebFilter` возвращает `X-Trace-Id`, сохраняет корректный входящий идентификатор или создаёт новый и помещает его в атрибуты запроса и Reactor Context. Core записывает уведомление в transactional outbox вместе с бизнес-изменением. Фоновый обработчик отправляет его через Feign и повторяет отправку после ошибки. Идентификатор сообщения постоянный, `ON CONFLICT DO NOTHING` исключает дубликаты при повторной доставке. Отправитель, как в лабораторной №1, фиксирует доставку в журнале; внешняя почта не подключена.

Resilience4j защищает Feign-вызовы и маршруты Gateway. После пяти вызовов при доле ошибок от 50% circuit breaker открывается на 10 секунд. Ошибки доступности возвращаются как HTTP 503; недоступность уведомлений оставляет записи в очереди. Настройки таймаутов и порогов находятся в Config Server.

## API

Сохраняются основные маршруты лабораторной №1: пользователи, персоны и профили, импорт, диалоги и сообщения, специалисты и консультации, справочники, модерация, метрики и уведомления. Текущий пользователь определяется по JWT из `Authorization: Bearer <token>`. Заголовок `X-User-Id` и параметр `userId` больше не авторизуют запросы.

Демо-пользователи создаются контекстом Liquibase `demo`:

| Роль | UUID |
| --- | --- |
| Администратор | `00000000-0000-0000-0000-00000000a001` |
| Специалист | `00000000-0000-0000-0000-00000000b001` |
| Клиент | `00000000-0000-0000-0000-00000000c001` |

Демо-записи сохраняются для совместимости с данными ЛР1. У старых учётных записей нет пароля: миграция ставит маркер `!`, который не принимается при входе. После первого входа супервайзер назначает им пароли через `PATCH /api/v1/users/{id}` с полем `password`.

## Авторизация и роли

1. В общем Swagger выберите `iam` и вызовите `POST /api/v1/auth/login` с телом `{"email":"...","password":"..."}`.
2. Скопируйте `accessToken` из ответа и вставьте его в **Authorize → bearerAuth**. Если переключаете спецификацию, авторизуйте её тем же токеном.
3. С JWT супервайзера вызовите `POST /api/v1/users`, передав `email`, `displayName`, `password` и необязательный список `roles`.

| Роль | Права |
| --- | --- |
| `ADMIN` — супервайзер | Создание пользователей, назначение ролей, блокировка, установка пароля, модерация и метрики |
| `USER` | Собственные персоны и диалоги, запись на консультации; нельзя создавать пользователей и управлять слотами специалиста |
| `SPECIALIST` | Свой профиль и слоты, работа с назначенными консультациями; нельзя создавать пользователей |

Чтение публичных справочников и активных профилей/свободных слотов специалистов остаётся доступным без входа. Изменения и персональные данные требуют JWT.

Роли можно совмещать. Создание пользователей проверяется в сервисном слое; присланное обычным пользователем поле `roles: ["ADMIN"]` не даёт права на регистрацию. Пользователь может менять своё имя, но не свои роли, статус или пароль; эти поля меняет супервайзер.

JWT подписывается HS256 и действует 15 минут. Проверяются подпись, срок, issuer, audience и тип доступа. Gateway и каждый бизнес-сервис проверяют JWT самостоятельно. REST-операции получают актуальные роли и состояние пользователя из IAM; блокировка прекращает доступ к ним даже со старым JWT. После смены пароля ранее выданные JWT действуют до истечения срока, если пользователь не заблокирован. После истечения токена нужен повторный вход.

Пароли хранятся только как BCrypt-хэши с индивидуальной солью и cost 12. В пользовательских ответах и токенах нет пароля или хэша. Ошибки входа возвращают 401, недостаток прав — 403. Для внешнего развёртывания перед Gateway нужен HTTPS.

Feign передаёт короткоживущий служебный JWT с отдельной областью `internal`. Пользовательский JWT не открывает `/internal/**`, служебный не открывает публичные `/api/**`, а Gateway запрещает внешние обращения к внутренним маршрутам.

Веб-интерфейс использует вход по email/паролю и хранит JWT в `sessionStorage`. Создание пользователя доступно на странице супервайзера. В браузере чат использует REST с обновлением истории каждые 5 секунд: браузерный WebSocket API не позволяет передать `Authorization`. WebSocket endpoint сохранён для клиентов, способных отправить Bearer-заголовок при handshake.

## Проверки

```sh
./gradlew test bootJar
python3 scripts/smoke-lab2.py
python3 scripts/smoke-lab2.py --resilience
```

Интеграционные тесты используют Testcontainers и требуют запущенный Docker. Для Colima при необходимости задайте `DOCKER_HOST=unix://$HOME/.colima/default/docker.sock` и `TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock`.

Тесты проверяют бизнес-правила core, API IAM, выполнение JPA на `boundedElastic`, R2DBC-пагинацию и доступ, идемпотентную доставку и повторные попытки outbox. Для smoke-проверки экспортируйте `ADMIN_EMAIL` и `ADMIN_PASSWORD` (либо `BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD`); `.env` автоматически читает Compose, но не Python-скрипт. Сквозная проверка требует запущенной системы и обращается к Gateway, Eureka и Config Server. Режим `--resilience` останавливает контейнер уведомлений, проверяет HTTP 503 и доставку накопленных событий после его запуска.

Тесты ЛР3 дополнительно проверяют подпись и срок JWT, запрет подмены `X-User-Id`, вход заблокированного пользователя, создание учётных записей только супервайзером, BCrypt и отсутствие паролей в ответах, разделение пользовательского и служебного доступа. `docs/demo.sh` принимает JWT демо-пользователей через `ADMIN_TOKEN`, `SPECIALIST_TOKEN`, `CLIENT_TOKEN`.
