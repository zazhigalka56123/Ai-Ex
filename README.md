# ai-ex («Привет, спишь?»)

Лабораторная работа №1: монолит на Spring Boot 4 и Kotlin с PostgreSQL.

## О чём проект

Идея простая: человек загружает переписку с бывшим или бывшей (экспорт из Telegram или WhatsApp), система разбирает, как этот человек писал, и собирает из этого чат-бота, который отвечает в той же манере. Пишешь в три часа ночи «привет, спишь?» и получаешь что-то вроде «я сплю вообще-то 🙄».

Тема эмоциональная, поэтому кроме самого бота в системе есть психологи, к которым можно записаться на консультацию, и администратор, который разбирает жалобы на контент. Итого четыре актора: клиент, специалист, администратор и сама ИИ-персона.

## Как устроена бизнес-логика

### Персона и загрузка переписки

Клиент создаёт персону: имя и кем этот человек был. Персона появляется в статусе `DRAFT`. Потом клиент загружает файл: `result.json` из Telegram Desktop, `.txt` из WhatsApp или обычный текст вида `Имя: сообщение`.

Дальше происходит разбор. Система определяет формат, вытаскивает сообщения и решает, какие из них принадлежат «ей». Нормализованные сообщения пишутся в базу одной транзакцией, чтобы не получилось импорта, загруженного наполовину. По её сообщениям считается статистика:

- средняя длина сообщений, эмодзи, капс, пишет ли с маленькой буквы;
- в какое время обычно пишет и как быстро отвечает;
- как часто встречаются ревность и нежность.

Отдельно отбираются характерные фразы. Всё, где есть телефоны, почты и ссылки, отбрасывается.

Из этой статистики собирается профиль персоны:

- черты, например `reply_speed = slow` или `jealousy = high`;
- автоматические теги вроде «сова» или «немногословная»;
- системный промпт для нейросети с примерами фраз.

Профиль версионируется: каждая новая загрузка даёт новую версию, а активна всегда ровно одна. За это отвечает и код, и уникальный индекс в базе. После этого персона переходит в `READY`.

Статусы персоны: `DRAFT → TRAINING → READY`. Новая загрузка снова переводит её в `TRAINING`, архивировать можно из любого состояния. Недопустимый переход возвращает `409`.

### Диалог

С готовой персоной можно открыть беседу и переписываться. Отправка одного сообщения устроена так:

1. Сообщение пользователя сохраняется короткой транзакцией.
2. Берутся последние 20 сообщений беседы.
3. Агент собирает промпт и вызывает нейросеть. Этот вызов идёт вне транзакции: запрос может длиться до 20 секунд, и держать всё это время соединение с базой нельзя.
4. Ответ сохраняется второй короткой транзакцией.

Каждый вызов нейросети записывается в `agent_runs`: модель, время ответа, токены, статус. Если нейросеть не ответила, клиент получает `503`, но его сообщение не теряется.

Есть защитные фильтры. Если в сообщении есть признаки того, что человеку совсем плохо, нейросеть вообще не вызывается. Пользователь получает ответ с предложением поговорить со специалистом, а сообщение автоматически уходит на модерацию. Опасный ответ самой модели заменяется нейтральным.

История беседы подгружается порциями, как лента в мессенджере: без общего количества, по курсору (время + id). Поэтому сообщения с одинаковым временем не теряются и не дублируются.

Переписываться можно и через WebSocket: `ws://localhost:8080/api/v1/conversations/{id}/ws?userId=<id>` (браузер не умеет ставить заголовки на сокет, поэтому пользователь передаётся параметром; `X-User-Id` тоже принимается). Пускают тех же, кому REST отдаёт беседу целиком: владельца и специалиста, которому её расшарили. Отправка идёт по тем же двум коротким транзакциям, что и `POST .../messages`, но сообщение пользователя приходит всем открытым вкладкам беседы сразу после сохранения, а не вместе с ответом.

| Кто | Событие |
| --- | --- |
| клиент → сервер | `{"type":"send","text":"привет, спишь?","requestId":"r-1"}` |
| сервер → все сокеты беседы | `{"type":"message","message":{…},"requestId":"r-1"}` — сообщение пользователя, после генерации ещё раз (защитные фильтры могли его пометить), затем ответ персоны |
| сервер → все сокеты беседы | `{"type":"typing","active":true}` на время генерации, потом `false` |
| сервер → отправитель | `{"type":"error","code":"LLM_UNAVAILABLE","detail":"…","requestId":"r-1"}` — коды те же, что в REST |

Рассылка работает в пределах одного экземпляра приложения; в лаб. 4 её заменит брокер.

По умолчанию вместо настоящей нейросети работает заглушка. Она собирает ответ из характерных фраз персоны, и одинаковый вопрос всегда даёт одинаковый ответ, поэтому для тестов и демо не нужны ни ключи, ни интернет. Настоящую модель (любую OpenAI-совместимую или локальную через Ollama) включают переменными окружения. Чтобы показать сбой, достаточно написать в сообщении `[[llm:down]]` или `[[llm:timeout]]`.

### Специалисты и консультации

Пользователь с ролью `SPECIALIST` заполняет профиль (специализации, цена за час) и публикует свободные слоты. Клиент выбирает слот и записывается. При записи он может «расшарить» беседу с персоной: только в этом случае специалист её видит.

Запись защищена от гонки: строка слота блокируется на время записи, а в базе стоит уникальный индекс. Если два клиента нажмут одновременно, второй получит `409 SLOT_TAKEN`. Консультация идёт по статусам `REQUESTED → CONFIRMED → DONE` (или `CANCELLED`). Специалист пишет резюме, клиент ставит оценку.

### Модерация и администратор

Клиент или специалист может пожаловаться на сообщение. Администратор видит очередь жалоб, включая автоматические от защитных фильтров. В беседах он видит только помеченные сообщения, остальную переписку ему не показывают.

По жалобе администратор выносит вердикт и при необходимости архивирует персону. Тогда профиль отключается, беседы закрываются, а загруженные сырые сообщения удаляются: каждый модуль чистит своё по событию. Ещё администратор ведёт справочники тегов и специализаций, блокирует пользователей и смотрит сводные метрики.

Клиенту приходят уведомления: переписка разобрана, персона готова, жалоба рассмотрена. Пока они просто сохраняются в базе, к лаб. 4 их заменит брокер сообщений.

### Кто делает запрос

Авторизации в лаб. 1 нет, текущий пользователь передаётся заголовком `X-User-Id`. В лаб. 3 его заменит JWT. Права при этом уже проверяются:

- без заголовка: `401`;
- не та роль: `403`;
- чужая персона или беседа: `404`, чтобы не выдавать, что такой объект вообще существует.

## Как устроен код

Это модульный монолит: одно приложение и одна база, но каждая часть предметной области вынесена в отдельный Gradle-модуль. Модули общаются только через свои модули `api`, то есть интерфейсы и DTO. У каждого модуля своя схема в PostgreSQL, внешних ключей между модулями нет. Это задел на лаб. 2, где модули превратятся в отдельные сервисы.

| Модуль | Что внутри |
| --- | --- |
| `app` | запуск приложения, обработка ошибок, Swagger |
| `common`, `web-common` | общие типы: ошибки, пагинация, события, текущий пользователь |
| `iam` | пользователи и роли |
| `persona` | персоны, черты, теги, версии профиля |
| `ingest` | загрузка и разбор переписки |
| `agent`, `llm` | генерация ответа и описание характера персоны, защитные фильтры, клиент нейросети; единственный модуль, который ходит к провайдеру |
| `dialog` | беседы и сообщения |
| `care` | специалисты, слоты, консультации |
| `admin` | жалобы, справочники, метрики |
| `notification` | уведомления |

Внутри каждого модуля одинаковые слои: `domain` (сущности и правила), `application` (сценарии и транзакции), `infrastructure` (работа с базой) и `web` (контроллеры).

Веб-интерфейс лежит в `app/src/main/resources/static` (`index.html`, `app.js`, `app.css`): одна страница на чистом JavaScript без сборки и зависимостей, её раздаёт само приложение, поэтому CORS не нужен. Он ходит в тот же REST API и передаёт выбранного пользователя в `X-User-Id`, чат работает через WebSocket (при обрыве переподключается, без сокета откатывается на REST), а набор разделов зависит от ролей: клиенту — персоны, беседы, специалисты и консультации, психологу — свой профиль, слоты и записи, администратору — модерация, пользователи, справочники и метрики.

Все ошибки возвращаются в одном формате (`application/problem+json`) с кодом ошибки и `traceId`, по которому запрос находится в логах.

## Как запустить

Нужен только Docker.

```bash
docker compose up --build
```

Первая сборка занимает несколько минут: Gradle внутри контейнера скачивает зависимости. Потом поднимаются PostgreSQL 17 и приложение, Liquibase создаёт таблицы, справочники и демо-данные.

- Веб-интерфейс: http://localhost:8080/ (вход под демо-пользователем одной кнопкой)
- Swagger: http://localhost:8080/swagger-ui.html (в выпадающем списке можно выбрать модуль)
- Health: http://localhost:8080/actuator/health

Демо-пользователи уже созданы. Их id подставляются в заголовок `X-User-Id`:

| Кто | `X-User-Id` |
| --- | --- |
| Администратор | `00000000-0000-0000-0000-00000000a001` |
| Психолог Анна (у неё уже есть профиль и слоты на завтра) | `00000000-0000-0000-0000-00000000b001` |
| Клиент | `00000000-0000-0000-0000-00000000c001` |

Весь сценарий защиты запускается одной командой: создать персону, загрузить переписку, пообщаться, записаться к психологу, пожаловаться, разобрать жалобу.

```bash
./docs/demo.sh
```

То же самое есть для IntelliJ в `docs/ai-ex.http`. Пример переписки для загрузки лежит в `docs/demo/telegram-masha.json`.

Подключить настоящую нейросеть:

```bash
AIEX_LLM_PROVIDER=openai AIEX_LLM_MODEL=gpt-4o-mini AIEX_LLM_API_KEY=sk-... docker compose up --build
```

Остальные настройки описаны в `.env.example`.

## Сборка и тесты без Docker Compose

Нужен JDK 21 (на более новых JDK эта версия Gradle не запускается) и запущенный Docker: тесты поднимают PostgreSQL через Testcontainers.

```bash
export JAVA_HOME=$(/usr/libexec/java_home -v 21)   # на macOS
./gradlew build
```

Команда `build` прогоняет ktlint, detekt, проверку границ модулей, ArchUnit и все тесты — большая часть интеграционные, на настоящей базе через Testcontainers. Порог покрытия 70% на проект и 60% на модуль, проверяется в `check`. Отчёт: `./gradlew koverHtmlReport`, потом открыть `build/reports/kover/html/index.html`.

Если вместо Docker Desktop стоит colima:

```bash
export DOCKER_HOST=unix://$HOME/.colima/default/docker.sock
export TESTCONTAINERS_DOCKER_SOCKET_OVERRIDE=/var/run/docker.sock
```

## Где что лежит

- `docs/architecture.md`: полный документ по архитектуре, модели данных, транзакциям и распределению работ;
- `docs/adr/`: почему приняты ключевые решения;
- `docs/implementation-guide.md`: договорённости по коду для команды;
- `docs/openapi/operations.snapshot.json`: все эндпоинты с кодами ответов (тест следит, чтобы они не менялись незаметно).
