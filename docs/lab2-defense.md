# Защита лабораторной №2

Команды ниже рассчитаны на уже запущенный Compose-стенд из корня репозитория. Они останавливают сервисы и меняют доступность приложения. Результаты ниже — ожидаемые, а не протокол выполненного запуска.

## Circuit Breaker: Notifications → IAM

`GET /api/v1/notifications` проверяет пользователя через Feign в IAM. Поэтому остановка IAM позволяет показать ошибку работающего бизнес-сервиса, а не просто ошибку маршрутизации Gateway.

Сначала успешный запрос:

```sh
curl -i -H 'X-User-Id: 00000000-0000-0000-0000-00000000c001' \
  http://localhost:8080/api/v1/notifications
```

Ожидается 200 и JSON-массив (пустой массив тоже нормален). Затем остановить зависимость:

```sh
docker compose stop iam-service
docker compose exec -T gateway wget -qO- http://notification-service:8082/actuator/health/readiness
```

Notifications должен оставаться UP. Повторить запрос шесть раз:

```sh
for attempt in 1 2 3 4 5 6; do
  curl -i -H 'X-User-Id: 00000000-0000-0000-0000-00000000c001' \
    http://localhost:8080/api/v1/notifications
done
```

Ожидается HTTP 503, `code: SERVICE_UNAVAILABLE` и `traceId`. Чтобы исключить подмену результата fallback-ом Gateway, обратиться напрямую к Notifications из контейнерной сети:

```sh
docker compose exec -T gateway wget -S -O /dev/null \
  --header 'X-User-Id: 00000000-0000-0000-0000-00000000c001' \
  http://notification-service:8082/api/v1/notifications
```

`wget` завершится с ненулевым кодом и напечатает HTTP 503 — здесь это ожидаемый результат. Проверить состояние breaker сразу после серии запросов:

```sh
docker compose exec -T gateway wget -qO- \
  'http://notification-service:8082/actuator/metrics/resilience4j.circuitbreaker.state?tag=state:open'
```

В `measurements` ожидается значение 1. При стандартной конфигурации учитываются последние 10 вызовов, минимум 5 вызовов, порог ошибок 50%, ожидание OPEN — 10 секунд, HALF_OPEN разрешает 2 пробных вызова. Настройки находятся в Config Server, а не в Kotlin-коде. Метрики доступны внутри Compose-сети, Gateway их наружу не маршрутизирует.

Восстановить IAM:

```sh
docker compose start iam-service
```

После готовности IAM и истечения интервала OPEN повторять запрос списка до двух успешных ответов 200. Затем запросить ту же метрику с `tag=state:closed`: ожидается значение 1. Перед следующим сценарием дождаться также успешного `GET /api/v1/personas` через Gateway: у core отдельный кэш обнаружения IAM, и его восстановление может занять больше времени. Для ожидания используются GET, а не повторные POST. Отдельно показанные 503 без метрики ещё не доказывают открытие breaker — они возможны и при обычной ошибке соединения.

Весь сценарий, включая восстановление сервисов в `finally` и отдельную проверку outbox:

```sh
python3 scripts/smoke-lab2.py --resilience
```

## Типы ответов

`Mono<T>` — один результат или отсутствие результата; `Flux<T>` — последовательность элементов. `Mono<Set<Long>>` технически допустим: один элемент потока является набором. Если контракт означает выдачу отдельных идентификаторов, лучше `Flux<Long>`. Превращение готового результата JPA в Flux не делает JDBC неблокирующим.

В Notifications репозиторий возвращает Flux записей R2DBC, сервис сохраняет этот контракт, контроллер выдаёт Flux DTO. HTTP-представление — JSON-массив, пагинация ограничивает выдачу 50 элементами, количество находится в заголовках. IAM также возвращает Flux<UserResponse>: JPA читает страницу на boundedElastic, после чего контроллер устанавливает заголовки пагинации и выдаёт её элементы через Flux. Транзакция остаётся на рабочем потоке. Это адаптация блокирующего JPA, а не неблокирующее чтение БД; Spring MVC формирует обычный JSON-массив.

ResponseEntity задаёт HTTP-статус, заголовки и тело. Возвращение DTO из RestController тоже допустимо и означает обычный 200. String из Controller без ResponseBody может означать имя представления; String из RestController — тело. Сервисный слой не должен зависеть от ResponseEntity.

## Миграции и OpenAPI

Liquibase нужен по условию первой лабораторной, которое сохраняется при декомпозиции. Он хранит историю применённых изменений и позволяет обновлять существующую БД без удаления данных. Notifications работает с данными через R2DBC, а Liquibase использует отдельное JDBC-соединение только для миграций. Первая миграция принимает старую таблицу; следующая добавляет ограничения целостности. Это покрыто отдельным интеграционным тестом со снимком старой схемы.

Operation задаёт понятное имя и описание операции в Swagger. ApiResponse описывает возможные HTTP-ответы и их схемы. Эти аннотации не устанавливают фактический HTTP-статус: 503 формирует обработчик ошибки, 201 — код создания пользователя. Схемы нужны, чтобы Swagger не описывал ошибку как успешный DTO. Типы схем и поведение HTTP проверяются разными тестами.

Notifications — история подтверждённых доставок. Публичные поля: id, type, payload, createdAt. Ожидание и повторы находятся в outbox core. Миграция notification-003-delivery-history удаляет status, attempts и sent_at, сохраняя записи, UUID и created_at. Если в старой таблице остались недоставленные записи, миграция останавливается до их разбора. Метрика notifications.sent считает записи истории.

## Среда и границы готовности

Версия Java задаётся каталогом: 21. Kotlin toolchain и тестовые JavaLauncher используют её; CI и Docker также используют Java 21. PostgreSQL в Compose и Testcontainers — 17-alpine. Нельзя считать тесты прошедшими по одной конфигурации: нужны отдельные запуск Gradle и проверка полного Compose-стенда.

Это учебная конфигурация второй лабы: X-User-Id не подтверждает личность пользователя, демо-регистрация открыта, используются демонстрационные учётные записи. Полноценная аутентификация относится к следующей лабораторной; текущий стенд нельзя публиковать как готовый защищённый продукт.
