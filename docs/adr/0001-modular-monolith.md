# ADR-0001. Модульный монолит с разделением `-api` / `-impl`

**Статус:** принято · **Дата:** 2026-09-24

## Контекст
Лаб. 1 требует монолит, лаб. 2 — распилить его на микросервисы, лаб. 4 — Clean Architecture. Переписывать систему дважды нельзя.

## Решение
Один Spring Boot-процесс и одна БД, но внутри — Gradle-модули на каждый bounded context: `iam`, `persona`, `ingest`, `agent`, `dialog`, `care`, `admin`, `notification`, `llm`.
Публичный контракт модуля — отдельный модуль `<name>-api` (интерфейсы + immutable DTO, без Spring/JPA); реализация — `<name>-impl`.
Модули зависят только от чужих `-api`, поэтому импорт чужой сущности — ошибка компиляции.

Границы проверяются трижды: графом Gradle, задачей `checkModuleBoundaries` (`-impl` → только `-api`/`common`/`web-common`/`llm`; `-api` без Spring) и ArchUnit-тестом в `app` (слои внутри модуля, чистота домена).

## Последствия
- В лаб. 2 каждый `-api` становится интерфейсом Feign-клиента с теми же методами и DTO — код вызывающих модулей не меняется.
- Каждая схема БД (`iam`, `persona`, …) переезжает в свою базу без миграции данных: межмодульных FK и JOIN нет.
- Цена — больше модулей и DTO-маппинга, чем в «плоском» монолите.
